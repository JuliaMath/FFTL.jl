Package size and load time ​

A Julia package that is precompiled stores its compiled code and its type information in a package image, a shared library in the compiled cache (~/.julia/compiled/v1.x/FFTL/*.dylib, .so on Linux). Loading the package maps that file and restores its contents. FFTL's image used to be 146 MB, 130 MB of it stored intermediate code, and using FFTL took 0.17 s. This page explains where that came from, what keeps it small now, what is left, and how to check it.

The steady-state ratios are interleaved A/B runs with one thread over 20 cases (Float64 and Float32, n = 64 … 2²⁰, 256², 100³). The full test suite passes on x86 with all of it in place, and the C library builds with juliac --trim and passes its differential test against FFTW.

Why the image was large ​

Julia drops the optimised intermediate code (IR) of a method that is not worth inlining when it writes the package image; only the machine code stays. There is one exception: a method that has no stored source keeps its IR. In Julia 1.13 (src/staticdata.c, the loop that decides what to discard) the test is def->source == NULL, and a @generated method has no source, because the source is produced by running its generator. Every precompiled specialisation of a @generated method therefore keeps its complete optimised IR in the image.

FFTL's stage kernels, run! and run_lanes! are @generated: the codelet of a radix is a long straight-line body that the generator builds for one radix, sign and vector type. The workload precompiled 1776 such specialisations with 469 000 statements in total, which is the 130 MB. The machine code of the whole package was 4.6 MB. This was checked in a small package with the same bodies written as 30 specialisations of 100 to 3000 statements: 281 MB as @generated, 13.8 MB as plain methods built with @eval. Which methods keep their IR is a property of Julia's package image writer; it may change in later Julia versions, so re-run the count below after an upgrade.

What keeps it small ​

  1. Plain methods for the fixed set. The stage kernels that RChain dispatches to (radix × sign × vector type, empty zero-input mask or full output mask) and the compiled chains of the smooth lengths up to SMALL_N are defined in src/kernel_methods.jl with @eval, from the same body-building functions the generators call. The @generated methods stay as the fallback for every other combination (other radices, vector types and chains), so behaviour is unchanged. A plain method keeps its (compressed) source and its machine code, not its optimised IR.

  2. Lazy radices. The codelets of the radices in LAZY_RADICES (17, 19, 23, 29, 31 by default; the preference lazy_radices, read in src/rchain.jl) are 54 % of the statements of the stage kernels and are rarely needed. They are not in the image. A call with such a codelet index reaches cstage_*_lazy, which finds a callable object for the (radix, sign, vector type) in a table and creates it at the first call; Julia compiles its kernel then. A first call of a length with such a factor takes 70–100 ms; later calls cost about 0.02 µs more than a precompiled codelet. Calling the stage kernel with run-time Val arguments instead of the table cost 0.22 µs per transform, 10 % at n = 1088. juliac compiles nothing at run time, so a program that is compiled with --trim sets the preference lazy_radices = []: every codelet is then compiled into it. libfftl/LocalPreferences.toml does this for the C library; a project that builds FFTL into its own trimmed library sets it in its LocalPreferences.toml (the project must have FFTL as a direct dependency):

    toml
    [FFTL]
lazy_radices = []

To add a radix, put it in RADICES; kernel_methods.jl defines its plain methods. To make a radix lazy, add it to the default of the preference in src/rchain.jl.

What is left ​

The 32 MB consist of about 3.8 MB for the package without the kernels, 8.6 MB for the definitions of the plain kernel methods (mostly their stored sources), and 19.6 MB that the precompile workload adds, of which 2.5 MB is machine code and the rest metadata of the compiled instances. With "none" as the workload (see Precompilation) the image is 12 MB.

Load time is not proportional to size. The 56–61 ms that FFTL itself takes with the workload fall to 20–26 ms without it, about 2 ms per MB of workload; SIMD.jl takes 20–26 ms, Dates 16–20 ms (it comes through PrecompileTools, Preferences and TOML), and AbstractFFTs 2–3 ms.

Further steps that were considered:

stepgaincost
methods generic in the element and vector type instead of one per vector typeabout 4 MB (stored sources ÷ 3)the compiler must fold ncomplex and sizeof of the type parameters; needs a speed check

Replacing the preference by environment variables did not shorten the load, and Julia does not notice a changed variable, so a stale image would stay in use. The pass plans do not take zero masks any more (their kernels were @generated with a mask per segment), so no pruned kernel exists to store.

Checking it ​

The size of the image is the size of the file in the compiled cache. To count the code instances of FFTL's own methods that hold optimised IR:

julia
using FFTL

function stored_ir(mod::Module)
    instances = 0; statements = 0
    for name in names(mod; all = true)
        isdefined(mod, name) || continue
        f = getfield(mod, name)
        f isa Function && parentmodule(f) === mod || continue
        for m in methods(f), mi in Base.specializations(m)
            mi isa Core.MethodInstance && isdefined(mi, :cache) || continue
            ci = mi.cache
            while true
                if isdefined(ci, :inferred) && ci.inferred isa Core.CodeInfo
                    instances += 1; statements += length(ci.inferred.code)
                end
                isdefined(ci, :next) || break
                ci = ci.next
            end
        end
    end
    (; instances, statements)
end

stored_ir(FFTL)    # (instances = 0, statements = 0) with the plain methods

Measure the effect of a change in a fresh depot (JULIA_DEPOT_PATH=scratch:$HOME/.julia), so that the cache of your normal depot is not overwritten, and compare the size of the new image file and the time Pkg.precompile() reports for FFTL.
